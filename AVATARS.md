The masks are original interpretations; no supplied screenshot or game texture is distributed in runtime.

## Host-exclusive D20 rule

`Hearth20AvatarStyle` defines the allowed cosmetic schema: robe, metal, chain and pendant. Only the authenticated `dm-local` host may equip `d20`. Players may select six robe colors and gold/silver Cuban, rope or layered chains. The D20 selector is constructed only in the host wardrobe; it does not exist in the player UI. Gold and silver remain available for the host's pendant.

The host never accepts a claimed role or target identity from a player's payload. `request_avatar` resolves the sender through the already authenticated peer mapping, rate-limits changes and passes the request to `_apply_avatar_as`. Player D20 requests, extra fields and role spoofing are rejected. Stored/public player styles are sanitized again, and the renderer independently refuses to draw a pendant on a player avatar. This rule is enforced in code, not a client setting players can toggle.

Open **Host / Join → Your wizard…**. The button remains accessible after Steam hosting begins. Host and player preferences are separate in the existing local profile. Confirmed host appearance and each participant's appearance are also stored in the campaign. Reconnecting automatically submits the remembered player appearance after the host advertises support. Cosmetic presence is a separate small reliable message; changing clothes does not retransmit maps or PNGs. Older peers that do not advertise avatar support are not sent the new RPC.

## Table presentation and privacy

The table is widened to 6.4 × 4.4 scene units. Connected participants other than the viewer occupy evenly spaced positions on a forward arc. Seats remain in the same shared room for map and casino; changing modes does not create another set of avatars. Disconnected campaign participants do not leave ghost seats. The local avatar is omitted.

Each other participant has a decorative paper sheet with generic rules, not a copy of their website or character data. The public roster contains only an anonymous per-view ID, display name, host/mine flags and approved appearance. It contains no sheet, browser image, signing key, token location, character stats or wallet balance. Presence still works while the player's map is covered or their token is in inventory.

The hood is a separate static part. Cartoon eye UV masks follow the black face surface; there is no mouth or head animation. **VoIP was cancelled by the user and is no longer pending.** There is no microphone capture or voice-amplitude hook. The hidden table stops processing when the map is focused. Jewelry links use instancing rather than a draw call for every link.

## Verification

### Physics-baked collar jewelry

`python tools/run_chain_bake.py` creates an isolated Jolt authoring project in `qa/chain-bake/authoring-project`; it does not change the game physics engine. The latest replacement run uses `--out qa/dm-pendant/chain-bake`. The full closed Cuban/rope loops use compound capsule-ring colliders, rigid bodies and pin joints against the actual fitted torso triangle mesh. One fixed clasp at the measured rear collar surface represents neck retention under the hood; the visible links are free to settle on the **outside** of the collar. Both loops in layered jewelry simulate together and collide with each other. D20 variants include the fitted replacement's weighted convex body.

Six variants run for 2880 steps each at 240 Hz, scaled up tenfold for small-link stability. The latest final-second motion band is below 0.1 mm for every variant. The runner preserves simulation frames/telemetry in the selected output folder and installs `source/hearth20/wizard_chain_bake.json` only when all six variants settle and the exact torso/pendant/script hashes match. Earlier rejected experiments in other `qa/chain-drape*` folders are diagnostic, not the current poses. The offline authoring process currently reports one retained RefCounted object at shutdown; keep that log visible. Native runtime jewelry verification closes without this warning.

`wizard_jewelry.gd` renders the captured positions/orientations in shared MultiMesh batches. There are no physics bodies, joints or chain simulations during gameplay. The weighted pendant's mount transform is separate from its placeholder visual model and includes an attachment marker, so a new supplied GLB can replace the charm without rebuilding the avatar or necklace. The isolated image reference is `Avatar References/Wizard-v1/04-dm-d20-pendant-only.png`; `dm_d20_pendant_placeholder.glb` and `pendant-attachment.json` provide the existing model/anchor for reference. The image includes a small bail and **no chain**. Generate/export only that single prop; keep its materials/textures embedded. Refit the replacement to the recorded mount, then verify or rebake contact if its physical silhouette changes materially.

`tools/run_source_check.py wizard_jewelry` checks native GPU transforms against captured physical poses, complete-loop connectivity, mesh binding, absence of runtime physics, shared batches, outward pendant normals and front/side/back screenshots for all six variants. Headless rendering has no actual MultiMesh GPU readback, so that particular assertion is native-only. Host-only pendant rules remain unchanged.
